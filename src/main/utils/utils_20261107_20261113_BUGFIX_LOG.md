## BUG-2026-11-12-002 日志写入链路的 4 个缺陷

| 字段 | 内容 |
| --- | --- |
| 出现 | 缺陷在 `src/main/utils/log.ts`（2026-04-22 `c3998302` 首次提交，含 `createWriteStream`）里；逐项引入提交未追溯 · `1.30.71` |
| 发现 | 2026-11-12 当天为 `log.ts` 补行为测试时暴露（修复提交 19:37 ~ 20:10） |
| 修复 | `f8a567d7`（#21）、`fcf5ba5b`（#22、#23）、`05fe7e6e`（#24）；11-13 10:05 装包 |

| #   | 缺陷与后果                                                                                                                              | 修复                                                         |
| --- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 21  | 写入流没有 `'error'` 监听、管道目标流出错也没人监听：重开文件的 ENOENT、磁盘满、权限错误都升级成主进程未捕获异常                      | 监听并摘掉坏流，下次写入重开；落盘失败只丢这一段             |
| 22  | 首次写入的大小被算了两遍，低于上限的单个大块被提前裁剪；裁剪失败后内容会被再追加一次；日志目录缺失不重试                              | 写入前读取大小；裁剪失败不再重复追加；目录缺失重试一次       |
| 23  | logfmt 里转义反斜杠后接 `n` / `r` / `t` 被解成控制字符（`C:\\new` 变成换行）                                                           | 单趟解码                                                     |
| 24  | `appendAppLog` 写入失败时 reject，133 处 `await` 它的调用方被连带中断（例如 TUN 权限恢复漏掉重启与系统代理兜底）                       | 日志只是尽力而为：写不进去只丢这一段，永不 reject            |

| 字段 | 内容 |
| --- | --- |
| 遗漏了什么 | #21 的修复（`f8a567d7`）提交说明里写着「`appendAppLog` 仍把失败报告给调用方」——只堵住了未捕获异常，没有改 reject 契约，33 分钟后才在 `05fe7e6e` 补上 #24；全仓 18 处 `appendAppLog(...).catch(() => {})` 因此成为冗余，尚未清理 |
| 导致了什么 | 若磁盘满或权限错误发生：#21 让主进程崩溃，#24 让无关业务（TUN 权限恢复、订阅更新心跳）被一条日志的失败中断；本周 `app-*.log`、`core-*.log` 里没有 `uncaughtException` / `ENOSPC` 字样，但日志写不进去时本来就不会留下记录，**线上是否发生过：无法判定** |
| 结构调整（行为保持，由测试锁住） | `log.ts` 473 → 320 行（含文件头，对比基线 `d99313a`）；logfmt 解析抽成 `logLineParseCore.ts`、裁剪规则抽成 `logFileSizeCore.trimLogContent`，均可直接测试；删除变异测试证明冗余的守卫 |
| 验证 | 全量 1677 用例 0 失败（2026-11-13 10:46）；变异测试 `logFileSizeCore` 100%（37/37）、`logLineParseCore` 92.6%、`log.ts` 95.3%（143/150，最后一次删除死语句之前测得），存活者为性能参数、空操作、仅影响性能的缓存跳过等等价变异；真实核心日志回放（只读）：本机 46.4 万行 mihomo 输出全部取出 level / msg / time，0 行残留转义字符，日志目录（105 MB）里没有解码器不认识的转义；**磁盘满 / 权限错误的真实触发：未验证**（只有单测用假流复现） |
| 反复 | 3 个修复提交（`f8a567d7`、`fcf5ba5b`、`05fe7e6e`）在 33 分钟内相继落地 |
| 踩坑经验 | ① 日志是旁路，必须尽力而为：它的失败不能改变业务流程（调用方 133 处）；② 修一类问题要把契约一次改干净——只堵一个出口（未捕获异常）而保留 reject，会在另一个出口（调用方被中断）再出问题；③ 带状态的写入链路（流、大小记账、裁剪）每个环节都要有「失败后下一次写入仍然正确」的测试 |

## BUG-2026-11-12-003 Reality 纯数字 short-id 被 YAML 解析成数字

| 字段 | 内容 |
| --- | --- |
| 出现 | 行标记器随 `yaml.ts` 首次提交（2025-08-04 `e572a8f5`，提交说明 handling unquoted short-id）进入仓库，只保护块风格，flow 风格盲区自那时存在；块列表误判（#25）的引入时间未追溯 · `1.30.71` |
| 发现 | 2026-11-12 当天为 `yaml.ts` 补测试与随机文档差分时暴露（修复提交 19:37、23:05） |
| 修复 | `9450ac1f`（#25，19:37）、`5a7fb057`（#28，23:05）；11-13 10:05 装包 |

| #   | 缺陷与后果                                                                                                                                                                                                              | 修复                                                                                               |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 25  | 代理内的块列表（如 `alpn`）被当成下一个代理，遮住随后的 `reality-opts`，`01234567` 被解析成数字 `1234567`                                                                                                              | `-` 仅当不比当前代理更深时才开始新代理                                                             |
| 28  | flow 风格（订阅转换器的主流写法；本机 3 份订阅文件共 218 行 `- {…}` 代理）的 `reality-opts: {…, short-id: 01234567}` 不在行标记器保护范围：`01234567` 变成 `1234567`，`12e3456` 变成 `Infinity`；内联 provider、锚点里同样没有保护（标记器只认顶层 `proxies:` 块） | 解析成文档树，`reality-opts` 里的 `short-id` 还原成原文（块 / flow / 锚点 / 合并键 / 任意位置都一样），删掉按缩进猜层级的行标记器 |

| 字段 | 内容 |
| --- | --- |
| 遗漏了什么 | #25 的修复仍然沿用「按行猜缩进层级」的行标记器，只补了块列表这一个形状，flow 风格 3 小时后才被发现（#28）；`short-id` 若自己是别名引用（`short-id: *x`）则按 YAML 规则解析，锚点是纯数字写法时仍会失真；其他字段的纯数字写法（如 `password: 00123`）解析后同样会丢前导零（本机 29 个 YAML 文件里 1013 个数字标量只有 1 个不能无损往返，是订阅信息里的 `expire`） |
| 导致了什么 | 若订阅里有 flow 风格的 Reality 节点且 short-id 以 0 开头或形如 `12e3456`：握手参数错误，节点不可用；**本机订阅里还没有 flow 风格的 Reality 节点，#28 未在线上命中过**，故没有已发生的用户症状 |
| 结构调整 | `yaml.ts` 83 → 49 行（含文件头，对比基线 `d99313a`）：`parseYaml` 改用 `parseDocument`，在文档树上还原 `reality-opts.short-id` 的原文，删除按行猜缩进层级的标记器；`yaml.test.ts` 与 `yamlShortIdGenerated.test.ts`（随机生成的 Reality 文档）锁住行为 |
| 验证 | 新旧实现差分（只读）：本机 29 个 YAML 文件（1.4 MB）新旧结果逐值相同；6000 个随机文档（块 / flow 风格、随机缩进与折行）新、旧、`yaml.parse` 三方一致；解析耗时不变（9 千行真实订阅最小值 29.9 → 30.4 ms；5000 节点合成文件块风格 473 → 477 ms、flow 风格 427 → 455 ms，**测量时机器负载 8~13，噪声较大**）；变异测试 `yaml` 97.1%（33/34，存活的 1 个是等价变异） |
| 反复 | 2 次（`9450ac1f` → `5a7fb057`），同一个根因：在文本上猜结构 |
| 踩坑经验 | ① 已经有语法树就在树上处理，不要在文本上猜缩进层级——行标记器先在块列表上出错（#25），又在 flow 风格上出错（#28）；② 订阅是外部输入，格式写法多样（块 / flow / 锚点 / 合并键），测试要覆盖「同一个数据的多种写法」，随机生成文档做差分比逐例补测更可靠；③ `parseYaml` 位于整个项目的中心，改动前后必须用真实文件和随机文档做新旧差分 |

## 已知边界

- 日志落盘失败是静默的（只丢这一段，没有计数或告警）。
- `short-id` 以外的字段、别名引用的纯数字写法仍会丢前导零（本机数据无此情形）。
- `src/main/utils` 目录没有 `_ARCH.md`（`doc.md` 要求每个模块文件夹都有；`src/main/config`、`resolve`、`service`、`sys` 同样缺），本次未创建，待用户决定。
