## BUG-2026-11-09-001 grok.com 打不开：探针把 Cloudflare 403 当成健康节点

**发生**：2026-11-09 16:30 起（1.30.71 旧构建，URLTest 香港组）

**现象**：grok.com 停在「请稍候… / 正在进行安全验证」；`cf-mitigated: challenge`；香港 12/12 节点 403，日/美/德 200。

**根因**：
1. `Sparkle-香港` 用 `https://grok.com` 做 `url-test` 探针，但未设 `expected-status`；mihomo 默认 `*`，403 挑战页被判定为健康。
2. 组成员由 `filter` 决定，探测失败不会剔除成员；组永远把流量钉在被挑战的节点。

**修复**：
- 新增独立 `grok 专用` 组（`select` + `sparkle-grok` provider），香港组只保留 X/Twitter/Stripe，探针改为 `https://x.com`。
- `sparkle-grok` provider 只收录 routed 验证通过的节点（真实 HEAD 200 且无 `cf-mitigated`），非香港优先、按 RTT 升序、上限 12。
- 稳态 60 秒只复核当前节点；网络超时重试一次；失败才按池内顺序切换；池内全灭才扩到全量发现（3 个可用即停）。

**验证**：`current=新加坡 I3 routed failed HTTP 403 cf-mitigated=challenge` → 自动切换；重启后连续 5 次 200；多轮 soak 30/30；全量测试 352/352。

**反复次数**：4 次（旧构建、重启、香港节点优先、叶子探针假阳性）。前三次只换了节点/组类型，没有换**测量口径**，因此反复复现。

**教训**：
- 只要探针与用户走的不是同一条路径、同一套响应判定，就必然出现「探测健康、页面打不开」。
- `expected-status` 默认 `*` 是隐形陷阱：任何 4xx/5xx 都会被当成可用。
- 节点名不可信（名为香港的节点可能出口日本）；按行为验证，不按名字推断。

## BUG-2026-11-10-001 合并订阅无规则导致 Google 直连撞墙

**发生**：2026-11-10 13:20（订阅更新后 1.30.71）

**现象**：`www.google.com` / `gemini.google.com` SSL EOF；`ipinfo.io` 返回本机 CN 出口；`gstatic` 204 正常。

**根因**：
1. 当前「合并版」profile 的 base `678a1sub001` 只有 `port/proxies/proxy-groups`，**没有任何 rules**；合并逻辑按设计沿用 base 规则 → 生成配置 0 条订阅规则。
2. 生成配置没有 `MATCH`，mihomo 对未命中流量默认 DIRECT；Google 无专属规则 → 直连撞墙。
3. 旧内核一直跑 13:20 之前的配置；14:47 装包重启后才加载新配置，因此表现为「装包后突然坏」。

**修复**：
- `ensureMatchFallbackRule`：生成配置若没有 `MATCH`，追加 `MATCH,🚀 节点选择`（缺省退 `自动选择` → `DIRECT`）。
- 全局覆写 `sparkle-match-fallback.js` 作为双保险（幂等，已有 MATCH 不动）。
- npm/Electron 镜像 `npmmirror.com` 直连覆写，避免构建卡在 TLS。

**验证**：配置最后一条 `MATCH,🚀 节点选择`；`www.google.com` 200/302；grok 200。

**教训**：
- 不能假设订阅一定带规则；配置生成必须有「MATCH 兜底」这一不变量。
- 运行态手改 `work/config.yaml` 是生成物，随时被覆盖；持久修复必须落在代码或覆写。

## BUG-2026-11-11-001 国内软件没走直连：内核长期运行旧规则

**发生**：2026-11-11（`SogouInput` → `otheve.beacon.qq.com`：`rule: Match`、链路 `自动选择` → `🚀 节点选择`）

**现象**：搜狗输入法等国内软件经代理出站。

**根因**：
1. 服务模式在 GUI 重启后保留旧内核；该内核只载入 131 条规则，磁盘 `config.yaml` 已有 3788 条。
2. 订阅刷新 / 应用订阅只热重载 provider（`reloadMihomoProfileProviders`），规则、分组变化从不让内核采用新配置。
3. 订阅 base 曾一度没有规则（见 BUG-2026-11-10-001），生成配置也没有国内基线，未命中流量全部走 `MATCH`。

**修复**：
- `runtimeConfigSync`：每次重新生成配置后按 `rules` / `sub-rules` / `rule-providers` / `proxy-groups` / `proxy-providers` 取指纹，变化则整配置重载；内核就绪时再用 `GET /rules` 条数与磁盘对账（跨进程兜底）；重载失败只记日志、不重启内核；重载后释放自动组固定。
- `cnDirectBaseline`：订阅没有任何国内感知规则（`GEOSITE/GEOIP,CN` 或 `RULE-SET`）时，在最后一条 `MATCH` 前补 `GEOSITE,CN,DIRECT` 与 `GEOIP,CN,DIRECT`。

**验证**：运行态磁盘 3788 条与内核 3788 条一致；隔离 mihomo（3788 条规则、26 组、5 provider）整配置重载 8 次耗时 13–39 ms，1323 次新建连接探测 0 失败；`mihomo -t` 通过；单测覆盖指纹判定与基线注入。

**状态**：代码已完成，尚未装包；重启后的运行态内核规则条数与磁盘一致（3788 = 3788），`GeoIP cn → 🎯 全球直连` 已有命中。

**教训**：「磁盘配置正确」不等于「内核在用它」；任何生成物落盘后都要有与运行态对账的环节。

## BUG-2026-11-11-002 `Sparkle-台湾` 节点超时很久不自动切换

**发生**：2026-11-11 11:15–11:41（内核日志 21 条 `Sparkle-台湾` 连续拨号失败告警）

**现象**：节点持续超时，Sparkle 没有换节点，靠手动切换恢复。

**根因**：
1. url-test 组的复测（`Sparkle-<地区>` 探测 Gemini / x.com）对该节点仍判存活，节点继续被选中，真实流量却持续超时。
2. 内核对「连续拨号失败」（同一组 5 秒内 ≥5 次）只打 warning 并复测一次，不会改选；高并发时同一时刻连发多条。
3. 旧 10 秒看门狗只处理「固定节点失活」，而该场景内核本就原生处理（URLTest 仅在固定节点存活时遵循 `fixed`），前提不成立。

**修复**：
- `groupFailover*`：订阅独立于界面日志级别的告警流（`/logs?level=warning`）；同一组 30 s 内的告警合并，180 s 内两次计数告警触发转移；在组内挑最近 15 分钟内探测成功、延迟最低的节点并固定，失败节点隔离 10 分钟，保留期满交还内核；用户固定且内核正在遵循的节点、非 url-test 组、`自动选择` 与专用组一律不动。
- `autoSwitchPolicy`：分组策略单一出处，故障转移范围与订阅 select 组的自动选路引用共用。
- 删除看门狗，固定释放改为按生命周期（`autoSwitchPinRelease`）。

**验证**：21 条真实告警折算为 6 次转移（11:15:52、11:18:46、11:21:15、11:24:52、11:37:13、11:40:04）；真实 mihomo v1.19.32 上告警帧经 `/logs?level=warning` 送达并被解析，URLTest 组固定 / 解除 / 非成员 400 与假设一致；引擎串行性经变异验证（去掉队列测试即失败）。

**状态**：代码已完成，尚未装包；引擎未在线上内核上实际触发过切换，仅用只读快照干跑确认 6 个 `Sparkle-*` url-test 组在范围内、其余分组不在范围内。

**教训**：「探测通过」不等于「真实流量可用」；内核给出的失败信号要接住，而不是再叠一层定时轮询。

## 复发反思（为什么修了很多次）

- 前 4 次 Grok 修复都在换「组类型/节点顺序/探测频率」，没有换**判定口径**；直到改为 mixed-port 真实 HEAD 请求，假阳性才消失。
- Google 问题被误判为「装包改坏」；实际是 13:20 订阅变体 + 14:47 重启加载的组合。证据是 `mihomo -t` 的前后对比与 base 规则数 0。
- 结论：**任何「健康/可用」指标必须与用户真实路径一致**；任何外部输入（订阅、节点名、CLI 依赖）都必须有兜底与可观测日志。
- 国内直连与台湾不切换同属一类：**运行态与磁盘不一致**、**探测通过但真实流量失败**；前者靠运行时配置对账，后者靠接住内核的连续拨号失败信号，而不是再叠一层定时轮询。
