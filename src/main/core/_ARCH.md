# src/main/core — 模块架构

Electron 主进程核心：mihomo 控制、订阅与配置生成、运行时配置与内核对账重载、自动选择延迟序与节点质量闸门、分组策略表与故障转移、Cursor / 邮件 / grok / agy 专用组与路由规则；邮件当前节点按需复测 993/465，grok 当前节点每 60 秒真实请求复核，agy 出口每拍（常驻进程 60 s、无头调度任务每次被唤起）先读用户真实会话日志里的地区拒绝、被拒即修复，pin 每 30min 经隐藏探测通道就地复测（不碰线上出口），内核拨号失败告警成风暴时提前触发修复，坏时按地区优先级修复、被拒节点 24 小时内垫底，地区组按需预热。

缺陷台账：仓库级 [BUGFIX_LOG.md](../../../BUGFIX_LOG.md)（用户可感知的网络僵死 / TUN 恢复等，例：BUG-2026-07-09-001 mihomo 出站池僵死）；本目录按「模块 + 7 日」归档的缺陷日志为 `core_<起>_<止>_BUGFIX_LOG.md`，最新一份 [core_20261114_20261120_BUGFIX_LOG.md](core_20261114_20261120_BUGFIX_LOG.md)（`自动选择` 钉住下载极慢的节点、AI API 直连关不掉（内置与覆写双来源）、`agy 专用` 出口失效 50 分钟未自动切换、AnyTLS 复用会话被 3 秒看门狗切断：根因、遗漏、踩坑、复发统计），上一份 [core_20261107_20261113_BUGFIX_LOG.md](core_20261107_20261113_BUGFIX_LOG.md)（版本与构建标识、根因、遗漏、踩坑清单、复发统计）。新缺陷先查同一周的文件，没有就按该命名新建。

Cursor 相关范围仅限：`🎯 Cursor 专用` 组（成员、仅手动选择、默认节点）与 Cursor 路由 / DNS 规则。Sparkle 不按 Cursor 流量做任何运行时干预（没有 keepalive / quiesce / 探针平面 / 恢复编排；故障转移引擎只依据内核按组上报的连续拨号失败告警，对 `Sparkle-<地区>` url-test 组一视同仁，不识别流量归属，也不改写 `🎯 Cursor 专用` 的选择）。

## 规则优先级（覆写 > 内置默认 > 订阅）

`generateProfile` 先应用覆写（`overrideProfile`：全局 + 单订阅，支持 YAML deepMerge 与 JS 脚本），再跑各注入步骤；注入的前置规则会排在订阅规则之前，因此内置默认必须"缺才加"：已有同类规则就不再补、不改写、不重复（`cnDirectBaseline` 在订阅已带国内感知规则时不补，`ensureMatchFallbackRule` 在已有 `MATCH` 时不补，`injectQuicTrafficRules` 在同文规则已存在时不重复）。AI API 端点（`api.commandcode.ai` / `opencode.ai` / `open-design.ai`）不再内置直连：是否直连只由用户态全局覆写 `sparkle-ai-direct`（`~/Library/Application Support/sparkle/override/`，不进仓库）决定，开启即对未被其它规则提及的域名前置 `DIRECT`，关闭即按订阅规则与兜底走代理，不存在「覆写关了内置又补回」的第二个来源。

### 构建漂移检测（R-52）

`com.sparkle.profile-scheduler` LaunchAgent 每 300s 直接执行 `/Applications/Sparkle.app`
的二进制（`--sparkle-profile-update-due`），绕开仓库执行 `generateProfile()`。源码改动
若未进入二进制，运行时仍执行旧逻辑且外部无信号——曾有一次修复因此被静默回退
（见 BUG-2026-10-01-003）。

判定 SSOT 在 `buildDriftPureCore`，`scripts` 与 `src` 共用，避免逻辑分叉：

| 组件                                  | 职责                                                                |
| ------------------------------------- | ------------------------------------------------------------------- |
| `src/main/core/buildDriftPureCore.ts` | 判定 SSOT：`detectBuildDrift` / `normalizeCommit` / `isBinaryRelevantPath`（纯函数，不碰 git） |
| `src/main/core/buildDriftGit.ts`      | git 读取（运行时与脚本共用）：`createGitRunner` / `readRepoGitFacts` / `listPathsChangedSince`（`git diff --name-only <app 提交> HEAD`）/ `evaluateBuildDrift` |
| `src/main/core/buildDriftCore.ts`     | 运行时入口：定位仓库、调 `evaluateBuildDrift`，写 `[BuildDrift]` 日志（进程内仅一次） |
| `src/main/core/factory.ts`            | `generateProfileImpl` 首步调用 `logBuildDriftAtStartup`             |
| `scripts/check-build-drift.ts`        | `pnpm run check:drift` 主动查询（按内容读 app.asar 内的构建标记），退出码 1 = 漂移 |

五种判定结果：`match`（commit 相同）/ `non_binary_ahead`（commit 不同，但 app 构建提交之后
只改了文档、测试、`src/shared/buildStamp.ts`，二进制内容没变，不算漂移）/ `commit_mismatch`
（app 旧于仓库，有会进二进制的改动，或查不到差异）/ `app_dirty`（构建时除 `buildStamp.ts` 外
还有未提交改动或未跟踪文件，构建不可复现）/ `app_unknown`（无 commit 事实的旧构建）。

- 「会进二进制」的判定偏保守：除 `*.md`、`*.test.*`、`buildStamp.ts` 外一律算；`extra/`、
  `resources/` 整目录算（随 `extraResources` 拷进 app，里面的文档也一样）。纯注释 / 格式化
  改动看不出来，会照常判为需要重建。
- app 构建提交在本仓库里解析不出来（被 gc、换了仓库）或 git 失败时不猜，按
  `commit_mismatch`（`ahead_check=unavailable`）处理。
- 仓库侧 dirty **不读也不算**漂移——commit 仍是权威标识，未提交改动本就不会进入 app。
- 构建流程「构建 → 安装 → 提交 buildStamp」会让 HEAD 比 app 的 commit 多一个提交，
  `non_binary_ahead` 就是为它而设，否则每次安装之后都会误报 `commit_mismatch`。
- 构建时的 dirty 不把 `src/shared/buildStamp.ts` 算进去：上一次构建留下、尚未提交的标记改动不会让
  下一次构建被记成 `app_dirty`；其余未提交改动与未跟踪文件都算脏，非 git 仓库或 git 失败按
  commit=unknown、dirty=true 处理。排除的路径与 `isBinaryRelevantPath` 认定的非二进制标记文件是同一个，
  由 `scripts/writeBuildStampCore.test.ts` 锁住。
